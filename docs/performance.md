# 性能度量与视频排障

性能比较应使用同一输入、模型、分辨率、设备、预热方式及并发负载，并分别记录稳态和首次初始化。单模型速度、完整处理速度和任务调度延迟是不同指标。

## 检测与任务负载

`Results.speed.inference` 只描述模型前向推理；`model.predict()` 还包含预处理和后处理；`Detector.detect()` 再包含去畸变与结果转换。完整感知处理还包含裁剪、去重或OCR提交和显示观察者；缓冲中的JPEG解码需要另计。不要用其中一个指标代替整条任务吞吐。

```bash
python -m airdrop.run benchmark-perception --images-dir input/frames --calib input/camera_calib.json --out output/detector.json --threads 4
```

输入图像与标定必须匹配。工具均匀抽样，单列模型预热，在固定样本上比较读取、解码、去畸变、predict与完整检测。它不启动OCR、飞控或任务状态机，不代表完整任务负载。

完整任务比较还需要同时运行实际OCR、记录和视频编码，统计侦查截止前的识别积压、截止后的帧/OCR排空、任务更新耗时和相邻更新间隔。等待任务启动确认属于外部状态等待，单独统计。调度晚点后补tick可能使平均间隔正常，因此必须看分位数和最大间隔。

`perception.opencv_threads` 是主进程设置，默认4。Ultralytics导入会关闭OpenCV多线程，因此运行入口在加载YOLO后、启动工作线程前应用配置；不在逐帧路径反复设置。该值影响整个主进程，不能按不同任务线程分别配置；OCR子进程与PyTorch线程配置不因此变化。线程数增加可能引入CPU争用，需结合完整任务的尾延迟判断。

## 去畸变

检测器按标定尺寸缓存定点映射表，逐帧调用OpenCV重采样；输入尺寸必须与标定和下游投影内参一致。预计算映射不等于免去逐像素插值。不要通过跳过校正、降低分辨率或改变图像坐标语义冒充等价提速。

## RTP与录屏

```bash
python -m airdrop.run qgc-video-benchmark --out output/rtp.json --seconds 6 --fps 12 --compose-delay 0.125
```

工具只在动态本地回环端口收取RTP包，比较正常与慢合成时的实际到达跨度、90kHz媒体时间、序列缺口及编码统计；不加载识别模型、不连接飞控。输出存在时拒绝覆盖。结果中的编码失败和收尾异常必须一并检查，成功收包不代表发布器全程无故障。

发布器的 rawvideo 输入按 FFmpeg 接收墙钟生成时间戳，输出使用 VFR 保留实际间隔；合成变慢或邮箱覆盖时，不再把剩余帧按连续帧号挤入较短的媒体时间。同一输入时间戳的帧可能被编码器同步层丢弃，因此发布器 `encoded` 统计表示完整写入管道的帧数，实际编码帧数应核对 RTP marker 或解码输出。配置 FPS 是合成目标速率；关键帧还按媒体秒周期触发，供接收端晚加入。

正常停止由编码线程完成当前整帧写入，关闭输入并等待 FFmpeg 排空末帧；超时才终止进程。强制终止和真实编码错误仍记录为失败，不能仅凭接收器退出码 0 宣称全程正常。完整流须保留严格解码结果，区分损坏的末帧、UDP 丢包和接收器采集收尾。

UDP 没有流结束标志。接收器被有界停止时，容器可能未写出最后的解析帧；此时以全部 RTP 原包的 marker 帧数为参照，检查序列连续性，重组完整 H.264 码流并严格解码，分别记录接收器和发布器的退出原因。不能仅凭恢复性解码成功排除损坏帧，也不能把接收器的停止退出码当作发布器故障。

墙钟/VFR 语义见 [FFmpeg 格式选项](https://ffmpeg.org/ffmpeg-formats.html#Format-Options)及[同步选项](https://ffmpeg.org/ffmpeg.html#Advanced-options)。长时间运行中的系统时钟跳变、外部网络抖动和不同编码器仍需分别验收。

排查QGC窗口异常时，应将同次编码流的本地文件与窗口录屏按画面编号匹配，再结合接收日志判断问题位于合成、RTP接收、解码、显示还是屏幕录制。发布邮箱丢弃为零不证明UDP接收零丢包；容器FPS也不证明实际发布速度。历史素材回放不验证真实设备和现场网络端到端延迟。
